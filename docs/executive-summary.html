Exactly how to make a submission into the GEMS Prize

Five steps. Nothing to install, nothing to configure. The portal rejects a file whose values are not inside [0, 1]; the files on this page are written so that cannot happen.

Step 1 — download gems66-h66-1-scarplet-veto-37654-20261011T203224Z-allfinite.zip

The submission form accepts “a single-band GeoTIFF (.tif), or a .zip file containing a single GeoTIFF”. The .zip is the smallest upload and contains exactly one file. If you prefer the bare raster, take gems66-h66-1-scarplet-veto-37654-20261011T203224Z-allfinite.tif; both are the same bytes inside the footprint.

Step 2 — open the submission form

https://www.drivendata.org/competitions/306/competition-doe-gems/submission/ → New submission → File to submit → choose the .zip.

Step 3 — why your last attempt failed, and why this one will not

The portal said Predicted values must be in range [0, 1]. That is a value check, not a format check, and it fires for three reasons — all of them fixed in the writer here:

  1. NaN outside the footprint. The problem page says data outside the bounds may be “null or nan”, but the range validator reads the whole array. A file with NaN outside the footprint fails 0 ≤ p ≤ 1 for those pixels. gems66-h66-1-scarplet-veto-37654-20261011T203224Z-allfinite.tif therefore writes 0.0 everywhere outside the footprint and carries no nodata tag; the NaN variant is kept only for spec-literalism (gems66-h66-1-scarplet-veto-37654-20261011T203224Z-nan.tif).
  2. Unnormalised units. A logit, a z-score or a 0–255 raster is out of range. The writer refuses to emit anything not already finite and inside [0,1] — src/gems52/submission_writer.py-style fail-closed, re-implemented in scripts/run_h66.py s5 and checked again by scripts/verify66.py.
  3. Wrong CRS/shape/transform or an HTML error page saved as .tif. Check the first bytes: a GeoTIFF starts with II*\0 or MM\0*; a Git-LFS pointer or an S3 error page starts with version https://git-lfs… or <?xml. Our receipt below pins the sha256 of the exact bytes.

Receipt for the bytes you are downloading: sha256 44d6dccbc27ce2e6dbe42794ed24c0f34c86aadb942c9b913afec08fb39953e1 · 3730×3292 · EPSG:32611 · dtype float32 · 37,654 positive pixels · min 0.0 max 1.0 · nodata None · all local checks passed true.

Step 4 — fill in the note (≤140 characters)

The form asks for “a short comment to help you or your team tell submissions apart later”. Paste exactly:

H66-1 LiDAR scarplet channels + cultural veto, 37654 dots >=300m off catalogue; HOLDOUT-DTI 0.048 vs 0.033 random; veto NEGATIVE

128 characters. Suggested submission name if your mirror asks for one: GEMSDOE66-H66-1-LIDAR-SCARPLET-VETO-37654.

Step 5 — decide: this file is NOT promoted

Uploading it is allowed by the rules (one submission per day per team is the only hard cadence limit in this family's notes; the weekly cap is shown on the submission page). But the honest read of the evidence is that this artifact scores in the 0.04–0.16 band where every LiDAR-scarp emission has landed, versus a standing 0.2778 and a board top of 0.4133. Spend a slot on the selector's pick, not on a negative-result lane.

Regenerate the file yourself (auditable end to end)

bash scripts/fetch_inputs.sh          # restores hash-pinned inputs into data/
python scripts/run_h66.py s0 s1 s2 s3 s4 s4b s5
python scripts/verify66.py --candidate docs/downloads/<file>.tif
python scripts/write_run_card.py && python scripts/build_site66.py

Requires: pip install -r requirements.txt (~2 GB RAM, 2 cores, no GPU; whole run ≈ 4 min). Every stage writes its own JSON into evidence/ before the next one starts.

Official format requirements being satisfied: single band · float32 · values in [0, 1] · EPSG:32611 · 100 m pixels · same bounds as the training data · see the problem page.
